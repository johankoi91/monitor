# 客户监控平台通知接入设计建议

目标是让客户平台持续、准确地维护每个节点的当前状态：首次接入能建立状态，异常和恢复能更新状态，断网后能够补齐，重复和乱序不会把状态改错。当前系统已经具备 HTTPS、独立签名密钥、节点通知、多地址订阅、持久化队列和接收去重，可以继续在现有 PostgreSQL 架构上完善。

## 本次实现：正常状态可以订阅

按用户确认，新增 `NORMAL`（正常状态）选项：首次启用后，使用下一次有效采集同步当前正常节点；持续正常不重复推送，恢复正常时再次通知。新增纳管且首次观测为正常的节点也会同步。

首次同步使用 `event_type=STATUS_SNAPSHOT`、`event_category=NORMAL`，表示当前状态快照，不伪造一次异常到正常的变化。后续变化继续使用 `STATUS_CHANGED`，恢复类为 `RECOVERED`。同时订阅正常和恢复的地址只收到一条恢复事件。`WEBHOOK_TEST` 仅用于通道测试，客户应排除其告警处理。

同步标识与订阅配置一同持久化；中心重启不会重复初始化。暂停再启用正常订阅、重新勾选正常、变更目标或密钥会重新建立该订阅的初始状态。添加其他地址或修改其他地址配置，不应使已经完成的正常初始化重发。正常订阅不自动为旧配置开启，由用户勾选。

“正常”表示当前配置的检查通过。只有容器运行检查时，它仅表示容器运行；客户平台不能据此推断 RTC/RTM 真实业务链路成功。

## 下一步最值得做的三件事

| 目标 | 当前设计的缺口 | 建议落地与验收 |
| --- | --- | --- |
| 能对账 | 新接收地址没有全部节点的初始视图；正常初始化只覆盖已订阅的正常节点。已有查询接口依赖页面会话，当前重启 Token 被禁止访问状态接口。基准移出节点也没有单独通知。 | 提供独立的只读接入 Token 和全量当前状态接口，包含当前纳管成员；客户首次接入、断线恢复和定期对账时拉取。客户仅用机器凭证即可重建页面所见状态，并能清除已移出台账的成员。 |
| 能补齐 | 当前总计四次短间隔尝试；失败后没有重投入口。队列上限为1000条，容量耗尽会记录丢弃。修改任一配置会按全局版本使旧队列失效，可能连带影响其他地址。 | 支持可配置的重试窗口、退避和失败重投；按接收配置独立管理队列和版本。模拟客户平台维护或网络中断后，应能补发或通过对账恢复最终状态；不把发送尝试等同于成功送达。 |
| 不会被旧消息覆盖 | 有 event_id 去重，但缺少每个逻辑节点的持久状态版本。旧事件重试可能晚于新事件到达。 | 增加单调递增的 node_version，并在中心持久化；客户只接受更新版本。增加稳定来源标识及消息版本，避免多个部署环境的私网IP、容器名重名，并支持后续字段扩展。 |

这三项形成最小接入闭环：通知负责及时更新，查询负责对账，版本负责重复和乱序处理。四次短重试继续作为当前协议约束保留；长重试及回放属于待实施优化。

## 消息契约要补足的说明

- `event_id` 是事件标识，同一事件的重试保持不变；多地址投递各自维护结果。
- 当前 `cluster + node_id` 可以在一个部署内定位。跨部署接入建议补充持久的 `source_id` 和稳定逻辑节点标识，IP与容器名作为展示信息；Docker 容器 ID 变化不应产生新的逻辑服务。
- 建议补充 `schema_version`、`node_version`、`check_level`。保留当前状态、采集时间和 stale，明确“容器正常”“Readiness正常”“采集未知”的区别。
- Agent 离线或数据过期表示采集不可判断，客户不能直接当作容器故障。恢复数据采集后应使用有效的新状态更新客户平台。
- 接收端宜允许未识别的新字段，依据 schema_version 处理不兼容变化。当前演示接收器采用严格字段校验，新增字段必须先升级接收端再升级发送端。
- 当前签名是原始请求体的 HMAC-SHA256/SHA1，接收端必须用原始字节验签，不能先解析再序列化验签。新接入优先校验 V2/SHA256。
- 当前只将 HTTP 200 + 合法 JSON 视为成功，202、204或200空响应均会重试。应在接入前与客户确认；客户平台响应格式固定时，使用接收适配服务衔接，不能假设任意平台的 Webhook 都可直接兼容。

## 客户接收端推荐处理流程

1. 接收 HTTPS 请求，校验签名和消息结构。
2. 使用 event_id 去重，将消息可靠保存，再返回 HTTP 200 和 JSON。
3. 异步将节点状态映射到客户平台；后续有 node_version 时，忽略旧版本事件。
4. 定期拉取当前状态进行对账，修复漏收、已移出成员或长期未知的状态。

签名验证失败返回401，暂时不能可靠保存返回5xx；同一事件的重复投递应返回成功。签名校验通过只证明来源和完整性，不等于客户平台已完成业务处理。

## 接入体验的后续优化

通知列表建议按接收配置显示最近成功时间、待发数量、最终失败数量，详情显示对应地址、HTTP状态、耗时、尝试次数和下次重试时间，并提供失败重投。当前只有粗粒度的网络/TLS失败原因和尝试次数，对客户排查证书、地址和平台报错还不够直接。

提供一份最小接入说明及可运行的接收示例，覆盖正常初始化、容器异常、采集异常、恢复、重复、乱序和断线恢复。若客户还需要 CPU、内存等历史图表，应另外对接指标采集或查询通道，避免把每次资源采样都塞入状态通知。

除“正常状态订阅”外，本文件其余建议为评审结论，尚未实施。
