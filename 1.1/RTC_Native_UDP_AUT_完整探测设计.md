# RTC Native UDP / AUT 完整探测设计

- 日期：2026-11-17
- 状态：Native 全链路已实现、已部署，独立环境和生产容器的真实 SDK 22 项验收均通过。
- 本期客户端：Agora-Golang-Server-SDK-2.6.6，Linux amd64。
- 本期覆盖：Native UDP、Native AUT 的 AP 接入、指定 Edge 直连及跨 Edge 音视频互通。
- Web SDK / Web Edge 探测后续再做，不计入本期必选覆盖范围。
- 探测对象：整体 RTC 服务。AP 和 Edge 是该服务下的接入路径，不分别建立容器健康结论，也不据此自动重启容器。

## 1. 服务接入模型

RTC 客户端有两种加入频道的途径。

### 1.1 经 AP 分配

```mermaid
flowchart LR
    C[Native 客户端] --> A[目标 AP]
    A --> R[返回适用于客户端模式的可用 Edge 地址和端口]
    R --> E[客户端连接被分配的 Edge]
    E --> J[加入频道并收发音视频]
```

UDP 模式请求 AP，验证 UDP 接入路径。AUT 模式必须先设置明确的客户端模式参数，再验证对应的 AP 分配和接入路径。此类用例不固定具体 Edge。

每轮使用新的 SDK 工作进程和独立频道，避免前一轮的 SDK 选路缓存影响本轮。记录两端最终连接的 Edge；同一 Service 的连接可能共享 SDK 接入状态，不假定一次用例必然产生两次独立 AP 请求。

### 1.2 指定 Edge 直连

```mermaid
flowchart LR
    C[Native 客户端] --> P[设置传输模式和单个 Edge 地址]
    P --> E[连接指定 Edge]
    E --> J[加入频道并收发音视频]
```

直连用例固定一个 Edge 的客户端地址和端口，并设置该 Edge 所需的 UDP 或 AUT 模式。需要证明实际走了指定路径。

AP 分配和 Edge 直连分别形成结果。随机加入成功不能证明其余实例可用；直连成功也不能代替 AP 分配链路的验证。

## 2. Edge 类型及本期范围

| AUT Edge | Native SDK，显式 AUT 模式 | 经 AP 加入、逐实例直连、跨 Edge 互通 |

## 4. AP 分组及 Edge 清单

### 4.1 数据来源

遍历中心所有已接入机器的容器发现数据，包含未纳管容器。筛选名称含 `media_edge` 的容器，从其最近一次完整有效启动参数提取：

- `--ap`：Edge 关联的 AP 分组地址。
- `--ip-for-client`：Edge 面向客户端的接入 IP。
- `--user-port`：该 Edge 的客户端端口。

复用已有加密启动参数记录，不额外保存一份完整启动参数。支持 `--参数 值` 和 `--参数=值`；读取 Docker 实际 Args，普通 shell 命令只做字面解析，不执行命令和变量。

### 4.2 分组结构

保持 `map[string][]Edge`，key 为 `--ap` 中的单个 AP IP。`--ap` 为逗号分隔列表时，校验并去重所有地址，再将同一实例分别关联到各 AP 分组；总实例数按身份去重，不能累加各组长度。同 AP 下的各个容器分别加入数组。同时返回显式 `edge_type` 和覆盖版本所需的身份字段。

```json
{
  "172.16.80.25": [
    {
      "edge_type": "udp",
      "ip_for_client": "111.230.192.59",
      "user_port": 4001,
      "agent_id": "rtc-192-59",
      "host_ip": "111.230.192.59",
      "container_name": "agora_udp_media_edge_1",
      "container_id": "当前容器实例标识",
      "snapshot_id": "当前启动配置标识",
      "stale": false
    },
    {
      "edge_type": "aut",
      "ip_for_client": "111.230.192.59",
      "user_port": 4701,
      "agent_id": "rtc-192-59",
      "host_ip": "111.230.192.59",
      "container_name": "agora_aut_media_edge_1",
      "container_id": "当前容器实例标识",
      "snapshot_id": "当前启动配置标识",
      "stale": false
    }
  ]
}
```

接口已返回上述类型、实例身份、配置标识、AP 分组、客户端 IP / 端口、来源机器 / 容器名和 `stale`。

类型根据明确的容器服务类型识别，例如 `agora_udp_media_edge_*`、`agora_aut_media_edge_*`、`agora_web_media_edge_*`。未知类型单独报告，不能仅凭端口号归类。

### 4.3 AP 分组与客户端入口分别保存

`--ap` 中的内网地址用于关联 Edge 清单，探针实际请求的 AP 可能使用另一个客户端入口 IP。本期 Native 自动覆盖的入口配置接受 IP 地址。

目标服务需要建立以下关联：

```text
AP 分组标识，例如 172.16.80.25
    → 探针可达的 AP 入口、证书校验域名
    → 该 AP 下已发现的 UDP / AUT Edge 清单
```

两者必须显式关联，不能仅凭字符串相等或来源机器 IP 推断。多个 AP 入口分别生成接入用例，避免一个入口的成功掩盖另一个入口的问题。

### 4.4 动态变化与缺失处理

- 每次根据最新观察重新生成发现 map，重复查询和周期上报不追加重复项。
- 参数缺失、不完整、容器 ID 或配置标识不匹配时，列入未解析项，不将旧容器参数归给新容器。
- 离线、停止或过期记录保留最后已知值并标记 `stale`，不将它直接当作当前可用实例。
- 探测覆盖集合区分“已纳入的期望实例”和“本次发现实例”。已有实例失联或消失先标记待验证；确认下线或权威部署清单更新后才移出期望集合。
- 本轮开始冻结覆盖清单与版本。新实例在下一轮或补测中进入覆盖，不能继承旧实例成功结论。
- 覆盖版本包含 AP 关联、Edge 类型、端点及容器身份 / 配置标识，不包含生成时间、心跳时间等持续变化字段。

## 5. 四类基础接入用例

| 用例 | 客户端模式 | 接入配置 | 验证内容 |
|---|---|---|---|
| AP_UDP | Native UDP | 指定 AP 入口，不设置固定 Edge | 本轮确实经过 AP 分配，加入并完成音视频收发 |
| AP_AUT | Native AUT | 明确设置 AUT 模式，指定 AP 入口，不固定 Edge | AUT 模式下的 AP 分配、加入及音视频收发 |
| DIRECT_UDP | Native UDP | 指定一个 UDP Edge | 实际连接该地址和端口，完成加入及音视频收发 |
| DIRECT_AUT | Native AUT | 明确设置 AUT 模式及一个 AUT Edge | 实际连接该 AUT 地址和端口，完成加入及音视频收发 |

AP 用例对每个配置的 AP 入口执行，每项只下发当前被测入口，避免 SDK 在多个 AP 入口之间回退而掩盖单个入口故障。直连用例遍历其关联清单中的全部 Native Edge。

以 2026-11-17 已发现的一个 AP 分组、3 个 UDP 和 3 个 AUT Edge 为例，在该组只有一个客户端 AP 入口的前提下：

- AP 基础用例：UDP、AUT 各 1 项，共 2 项。
- 直连基础用例：3 个 UDP + 3 个 AUT，共 6 项。
- 基础覆盖合计 8 项；3 个 Web Edge 保留发现信息，不计入本期执行与覆盖分母。
- 跨 Edge 用例另行计算，不包含在这 8 项中。

## 6. 路径参数与实际选路验证

### 6.1 UDP 与 AUT 参数按用例隔离

每个用例独立构造参数，记录模式、方法、入参和实际返回值。目标级单一 `disable_aut` 开关无法同时表达 UDP 与 AUT 的测试意图；扩展时改由内部模式配置生成各用例参数，既有 UDP 行为按迁移规则保留。

UDP 用例明确选择 UDP；AUT 用例明确选择 AUT。`DisableAut=false` 仅表示允许 AUT，不能据此声明强制 AUT 或 AUT 覆盖通过。原始参数 JSON 和底层开关由集成工程管理，页面不增加 SDK 私参编辑框。

### 6.2 已确认参数与调用时序

用户确认并经真实 SDK 验证：`rtc.enable_nasa2=false` 关闭 AUT、选择 UDP；`true` 强制 AUT，也是 SDK 默认值。直连再设置单元素 `rtc.vos_list=["ip_for_client:user_port"]`。两端分别在自己的 `conn.GetAgoraParameter()` 上调用 `SetParameters`，随后 Connect。

一个 Service 在创建连接后统一调用一次 `SetLocalAccessPoint`；AP 用例只配置本用例的 AP 客户端 IP。直连和跨 Edge 用例保留该目标的 AP 公共配置，SDK 内部接入流程由 SDK 自行处理。没有额外的“AP 完全不可达仍须加入”要求。

不同 UDP Edge、不同 AUT Edge，以及 UDP / AUT 混合连接都已通过。现场 AUT Edge 在 socket 层也使用 UDP；Edge 类型根据发现身份和连接参数确认，不能将 AUT 等同于 TCP。

### 6.3 AP 与直连的验收要求

- AP 用例确认本轮有 AP 接入 / 分配证据，并记录最终连接的 Edge。
- 直连用例确认实际连接的 IP、端口和模式与期望一致。
- 直连以设置 `rtc.vos_list` 并观察到指定 Edge 的有效媒体流量为依据；允许 SDK 辅助访问配置的 AP，该访问不导致直连失败。
- 严格目标验证须限制回退，并确认私有化模式的实际行为。`ConnectivityFirst` 允许回退，仅设置 AP 地址不能证明始终经过该目标；`LocalOnly` 的适用行为也需结合现场版本验证。
- SDK 调用返回成功只证明配置调用成功。优先使用 SDK 已有回调和可解析日志确认实际选路；缺少证据时明确标记未确认，必要时通过隔离用例抓包完成能力验收。
- 回退到其他地址、其他传输类型或目标部署之外时，不得将指定路径标为通过。

## 7. 跨 Edge 音视频互通

### 7.1 覆盖目的

同一 Edge 内部收发通过后，仍可能存在不同 Edge 之间的转发故障。因此在基础接入验证之外增加：

| 类型组合 | 示例 | 方向 |
|---|---|---|
| UDP ↔ UDP | UDP 4001 与 UDP 4002 | 分别验证两个方向 |
| AUT ↔ AUT | AUT 4701 与 AUT 4702 | 分别验证两个方向 |
| UDP ↔ AUT | UDP 4001 与 AUT 4701 | 分别验证两个方向 |

发送端和接收端分别直连各自指定的 Edge，使用同一测试频道。初期将两个方向作为两个独立单向用例执行，沿用“一端发、一端收”；每个方向均须实际收到音频和视频。

### 7.2 当前默认采用动态环形覆盖

按目标清单中的 Native 实例数 N 构造有向环，每条边为一个独立频道的单向音视频用例。4 个 UDP、4 个 AUT 时：

```text
U1 → U2 → U3 → U4 → A1 → A2 → A3 → A4 → U1
```

共 N 项，每个实例各承担一次发送和接收，覆盖同类及 UDP/AUT 互通。相邻轮次反转同一环；后续轮次以轮次为种子打乱各类型内的顺序。环内不是媒体逐跳转发，执行顺序不受箭头顺序约束。

只有两个实例时构造 A→B、B→A；不足两个实例时报告跨 Edge 覆盖不足。每轮清单、连接路由及频道独立。该策略验证本轮选定的环，不声明所有两两组合或每对双向均已通过。此前 3+3 的 14 项、4+4 的 20 项参考拓扑仅作为历史验收记录，不再用于默认计划。

## 8. 探测服务、多 Connection 与工作进程

### 8.1 SDK 已确认支持单进程多连接

SDK 文档明确规定一个进程初始化一个 Service，Service 内可随时创建和销毁多个 Connection。官方 `go_sdk/examples/multi_cons_rtx` 示例先全局 Initialize，再以 goroutine 并发启动多个任务，各任务创建自己的 RtcConnection，收发音视频也使用独立 goroutine。

因此，同一个容器中的一个 SDK 进程可以维护多个 Connection，不要求每个 Connection 对应一个独立进程或固定 OS 线程。所有连接共享 Service 的 AppID 和公共配置。

SDK 内部线程通过回调进入 Go，并按原生句柄找到对应 Connection。业务侧为各 Connection 管理上下文、状态、送帧 goroutine 和事件队列；共享统计使用同步保护。同一 Connection 的 Connect、Disconnect、Release 等生命周期串行管理，释放前先停止相关业务 goroutine；Service 在全部连接结束后统一释放。

SDK 文档明确要求 observer / 回调中不调用 SDK API、不执行 CPU 耗时工作。回调只复制必要数据并投递事件，后续操作由业务 goroutine 执行。

### 8.2 参数具有 Service 与 Connection 两种入口

源码同时提供：

```go
// Service 级参数句柄。
agoraservice.GetAgoraParameter()

// 各 Connection 自己的参数句柄，底层由 agora_rtc_conn_get_agora_parameter 获取。
conn.GetAgoraParameter()
```

既有手动 UDP 范围探测使用 Service 级入口。Native 完整覆盖使用 Connection 级入口，分别设置 `rtc.vos_list` 和 `rtc.enable_nasa2`；公共 Service 参数只设置一次。

真实媒体流量与解码回调已经确认连接级 VOS 和模式隔离有效。另用原生 C API 连续创建两个 Service，得到相同 Service 句柄及参数句柄，说明当前发布包不能通过重复创建 Service 隔离公共配置。集成工程未修改 vendor 源码。

### 8.3 当前执行方案及适用边界

| 场景 | 执行方案 |
|---|---|
| 两端模式及参数相同的基础用例 | 一个 worker、一个 Service、两个 Connection |
| 连接级路由隔离验证通过的跨 Edge / 跨模式用例 | 一个 worker、一个 Service、两个独立配置的 Connection，以 goroutine 协同执行 |
| 所需参数仅支持 Service 级、连接间存在串扰，或要求独立 AppID / 公共配置 | 同一探测服务启动两个隔离 worker，各自一个 Service / Connection |

本期 AP、直连和跨 Edge 均采用一个 worker、一个 Service、两个 Connection，容量为 1 即可执行。真实验收覆盖不同 VOS、同类/混合模式及双向跨 Edge。以后扩展参数或修改连接生命周期时，应重新验证隔离能力，不把现有结论推广到 SDK 的所有私参。

无论采用单进程还是隔离 worker，目标仍是一个探测服务及其与中心的一条 WSS 控制连接。任务只关联一个 `probe_id`，收发角色由内部执行计划产生。两端使用同一频道、固定的不同 UID，准备完成后统一开始送帧，取消或超时清理整组连接。

`capacity` 继续按 worker 进程数计算，同时评估单 worker 的连接数量与资源上限。单 worker 多 Connection 方案验证通过后，容量为 1 也可执行该能力范围内的跨 Edge 用例；需要两个隔离 worker 的用例则必须成对预留两个槽位，不能启动半组。两种方案的 CPU、内存及清理行为均需实测。

## 9. 单用例过程与判据

统一过程：

```text
冻结目标与覆盖版本
  → 校验探针能力、素材和资源，预留完整用例的 worker 槽位
  → 初始化 SDK
  → 设置客户端模式和接入路径
  → 两端加入频道
  → 订阅、发布，开始发送固定素材
  → 核对远端身份、音视频证据及实际选路
  → 停止发送、断开、释放对象
  → 上报结果并回捞执行日志
```

每个用例使用独立频道，UID 继续由系统固定为 10001 / 10002，不增加用户输入。跨 Edge 的反向用例使用新的频道，并交换两端对应的 Edge。

媒体继续使用固定官方 demo PCM 与 I420 文件。每个方向的通过条件：

- 两端均完成本轮连接，频道和预期对端身份正确。
- 发布与送帧调用正常。
- 接收至少 1 秒有效音频、至少 5 帧有效视频。
- 接入模式和实际路径符合该用例要求。
- 清理、进程退出与记录完整性均明确上报。

缺少任一种媒体即业务失败。初始化失败、本地配置校验失败、素材缺失、探针资源或进程异常归为执行错误。只有取得明确证据才能细分 AP 阶段与 Edge 阶段；统一的 JOIN_TIMEOUT 不能直接改写成“AP 进程故障”。

## 10. 执行计划与证据字段

中心已将用户任务编译为内部用例，字段映射如下；每个用例携带完整冻结快照。

| 字段 | 用途 |
|---|---|
| `coverage_version` | 冻结本轮 AP 关联、实例身份及端点集合 |
| `case_kind` | `AP_JOIN` / `DIRECT_JOIN` / `CROSS_EDGE_MEDIA` |
| `ap_group` | 对应发现 map 的 AP 分组 |
| `ap_entrypoint` | 本用例实际验证的客户端 AP 入口 |
| `sender.transport` / `receiver.transport` | 各角色的 `udp` / `aut` 模式 |
| `sender` / `receiver` | 直连及互通用例期望的地址、端口和实例身份 |
| `sender_route.observed` / `receiver_route.observed` | SDK / 网络证据确认的实际端点 |
| `sender_route.status` / `receiver_route.status` | `VERIFIED` / `MISMATCH` / `UNVERIFIED` |
| 发送 / 接收角色 | 本次单向媒体流的发送与接收关系 |

AP 用例不预设被分配的具体 Edge，实际端点须属于该组及相应类型的覆盖清单；分配到未知地址时明确展示，不能自动把该地址认定为已发现实例。

复用现有 `target_id → task_id → run_id → 角色 / worker` 归属、API / 回调记录、阶段耗时、帧计数、SDK 日志及诊断 ZIP。同一用例中共享 Service 的收发连接只生成一个 Service 诊断包，包内按角色保留调用、回调与结果，共享原生日志仅保存一套。多连接和跨 worker 数据均按用例、角色与各自连接分别关联。

数据保留沿用现有执行记录、有限诊断日志和当前健康状态的机制。维持已经移除“状态与操作审计”的约束，不恢复其页面、接口、保留字段、队列或数据库表。

## 11. 周期、容量与调度

采用三种执行节奏（同一阶段内可并发执行不同用例）：

| 类别 | 调度原则 |
|---|---|
| AP 接入 | 短周期，及时发现接入 / 分配链路异常；各 AP 入口、模式分别计数 |
| Edge 直连 | 按冻结清单完成一轮，失败后继续检查后续实例 |
| 跨 Edge 互通 | 按本轮有向环轮巡，可采用较长周期 |

三类间隔从各自整轮完成后起算，默认 AP 180 秒、固定 Edge 900 秒、跨 Edge 1800 秒；已部署主任务保留 AP 600 秒。周期由用例数量、单项超时、worker 数、清理时间和并发上限计算，并校验同一探针所有已启用任务的最坏合计负载。发现集合扩张导致预算不足时，轮巡显示未知并保留 AP 优先执行。每项结束预留 5 秒冷却，不在长轮巡中饿死 AP 检查。

本例 8 个基础用例、单项业务超时 30 秒、串行执行时，仅业务超时预算就是 240 秒，另需初始化、清理和控制时间。再加入 14 个单向互通用例后，不能仍使用原来的 60 秒整轮周期。

短周期 AP 用例优先领取空闲工作槽位，避免长轮巡阻塞 AP 检查，同时为轮巡保留进度预算，避免被短周期任务长期挤占。相同任务 / 计划不重入；按已验证的执行方案预留整个用例所需的 worker 和连接预算，需要两个隔离 worker 时必须成对取得槽位。

修改目标配置、覆盖版本变化、任务停用或中心重启时，旧用例按现有规则中止 / 失效；旧版本的迟到结果不能更新新覆盖状态。

## 12. 状态聚合及故障表达

### 12.1 分别计算后聚合

AP 路径按各自周期累计失败 / 恢复。Edge 直连沿用“一次完整轮巡计一轮”；跨 Edge 按本轮环形拓扑完成一轮后计数。默认连续 3 次业务失败确认异常、2 次成功恢复，具体阈值仍由任务设置。

每个必选覆盖项保留当前结果、版本和新鲜度，再聚合为本期 Native 整体状态：

1. 存在达到确认阈值的业务失败：异常，即使同时存在其他未知项，也不能掩盖已确认失败。
2. 没有已确认失败，但有未完成、尚未建立有效基线、能力未就绪、实际路径未确认或过期项：未知。
3. 所有必选项均按现有防抖规则正常，证据完整、新鲜且版本匹配：正常。

确认中的失败继续显示次数与原因，不作为新的有效成功证据；首次建立状态仍遵循现有未知 / 正常基线规则。

配置清单发生变化后，新增实例显示待覆盖。过期成功、Web 未实施和不支持的 AUT 能力不能填充为 Native 必选用例成功。

### 12.2 用路径证据辅助定位

| 结果组合 | 可以表达的结论 |
|---|---|
| AP 接入失败，相关直连通过 | AP 接入 / 分配链路验证失败 |
| AP 接入通过，个别 Edge 直连失败 | 存在特定 Edge 接入路径异常 |
| 同 Edge 基础验证通过，跨 Edge 失败 | 对应实例之间的媒体互通路径异常 |
| UDP 通过，AUT 失败 | AUT 接入或互通路径异常，按失败阶段展示 |
| SDK 参数不支持、探针资源不足、路径证据缺失 | 探测执行错误或覆盖未知 |

这些结论用于整体 RTC 服务的功能诊断，不直接推断故障发生在某个容器进程内部。

## 16. 跨 Edge 精简与动态多进程并发（已实现）

本节已实现并发布。跨 Edge 项数和单任务并发数均根据 Native 清单动态计算，不固定为 8；资源不足时排队。此前耗时估算保留为方案背景，实际验收结果见文末。

### 16.1 默认按 N 个 Native 实例构造 N 项环形覆盖

当前 4 个 UDP、4 个 AUT 实例，默认构造一个包含全部实例的有向环：

```text
U1 → U2 → U3 → U4 → A1 → A2 → A3 → A4 → U1
```

每条箭头是一个独立频道、一次单向音视频用例，共 8 项。每个实例在本轮各承担一次发送、一次接收；包含 UDP→UDP、AUT→AUT、UDP→AUT 和 AUT→UDP。AP 2 项及全部实例直连 8 项保持，因此一轮合计 18 项。

环顺序和方向按轮次轮换，轮次内冻结计划。不能将“各实例发送/接收通过”表述为“所有 Edge 配对或同一对的两个方向均已通过”；原参考拓扑验证的部分配对在当前精简轮次不会执行。低频深度检查可保留原参考拓扑，但应单独配置、展示和计算预算，不偷偷计入默认 8 项。

至少两个实例才生成跨 Edge 用例。只存在一种模式时构造该类型的环；只有两个实例时自然生成 A→B、B→A。多 AP 分组分别构造各自环；实例新增、替换、离线及覆盖版本失效的规则沿用现有实现。

### 16.2 同一探测服务内按清单并发 SDK 子进程

保持一个探针容器、一个 probe_id 和一条 WSS。父进程只管理任务、证据和上传；每个子进程独立执行一个用例。下图仅示意两个槽位，实际数量按清单和资源确定：

```text
探针主进程（WSS / 调度 / 上报）
 ├─ SDK worker 1：Service 1 + 发送/接收两个 Connection → 用例 A
 └─ SDK worker 2：Service 2 + 发送/接收两个 Connection → 用例 B
```

各 Service 分属各自 OS 进程，SDK 全局配置、缓存和原生句柄分别隔离。每个用例完成后进程退出，再启动下一项。无需在同一进程重复创建 Service，也不修改 SDK 源码。

并发单位是完整用例，一个用例的两端保留在同一 worker。两端连接级 VOS / AUT 隔离已经验证；此调整优先复用现有执行逻辑，避免引入跨进程两端开始同步和半组资源预留。各用例使用独立频道、工作目录、诊断文件和进程级选路捕获。事件继续按 task/run/case/worker/role 归属，不能合并其他用例的接收帧作为通过证据。

### 16.3 已同步修改中心调度

客户端当前已有 capacity 及多个子进程的管理能力，Native 调度原有“一个任务一个活动子用例”和任务级 NextCaseAt 冷却限制现已移除。当前行为：

- 统一按探针剩余槽位派发，允许同一任务的不同用例占据不同槽位，单任务上限为 `min(Native 期望实例数, 探针资源容量, 中心全局容量)`。
- AP 优先领取下一个空闲槽位；DIRECT / CROSS 按预算继续推进，不强杀已有用例。
- 将任务级冷却改为槽位冷却，避免一个用例结束后阻塞整个任务；最后一项完成后再结束本类整轮。
- 配额同时约束中心全局、探针、单任务；资源不足时等待，不能重复派发同一个 pending 用例。
- 停用、取消、超时、重启与覆盖变化时取消所有关联子进程，旧版本迟到结果不能更新当前状态。一个子进程崩溃不应终止其他用例。
- 根据实际并发槽位重新计算阶段期限、完成后间隔与最坏进程占用预算；预算不能仅将串行总耗时除以并发数。

现场探针采用 `RTC_PROBE_CAPACITY=auto`，容器资源为 8 vCPU / 4 GiB、PID 上限 2048，按当前 8 个 Native 实例派发并行用例；实例减少时并发同步减少，超过资源额度时排队。资源容量按 CPU/cgroup 配额、内存预算计算，与 Edge 数解耦，硬上限 64。中心总容量设为 32，并配置 2 vCPU / 512 MiB。

### 16.4 验收与预期

以当前约 7 分 50 秒 / 30 项的实测作参考，精简后 18 项串行约 4–5 分钟；两个 worker 并发估计约 2–3 分钟，尚未实测，不作为上线承诺。

实施验收包括：8 个实例每轮各发送/接收一次；类型组合齐全；并发用例频道、VOS、模式与日志隔离；容量上限不超发；AP 不被轮巡饿死；一个用例失败后其他用例完成；多子进程取消及旧版本隔离；所有方向均满足原有音频、视频和实际路径判据。页面需明确标注环形覆盖和实际用例数。

### 16.5 并发控制链路修正

首轮 8 进程实测发现 SDK 加入仅约 0.3 秒，等待中心开始指令却达二十多秒，导致 30 秒用例超时。排查确认中心原 0.5 核额度持续打满，并存在逐事件持久化开销。修正为控制消息优先、突发事件合并持久化；API/回调明细及事件顺序保持保存，持久化成功后才发布就绪和结果。中心资源提高至 2 核；开始指令过迟导致媒体时间不足归为 CONTROL_START_TOO_LATE 执行错误，不计为 RTC 业务故障。

## 17. 同一 Service 的日志合并（2026-11-18 已发布）

同一个 SDK worker 内只有一个 Service、两个 Connection，因此按 Service 回捞一次。当前 18 个用例对应 18 个日志包，不再为每个用例分别回捞发送端、接收端两份包。

- 中心在下发任务时通过 `shared_service_logs_v1` 能力捕获 `job.log_scope=service`，持久化后按该规则生成一条 `scope=service`、`endpoint_role=pair` 的日志请求，重复请求去重。
- 探针合并两端 `sdk-api.jsonl` 与 `events.jsonl`，按发生时间及源序号排序并保留角色、调用关联和完整参数；`result.json` 包含 sender / receiver 两端结果。
- `sdk/agorasdk.log`、`sdk/agoraapi.log` 等共享原生日志各取一次，保留二进制文件边界；进程输出和选路元数据也只取一次。
- manifest 包含公共执行快照、收发 UID / 频道及文件摘要。中心同时校验两端归属，不能混入其他频道、配置或用例。旧的按角色日志保持兼容读取，新执行使用合并格式。
- 页面每个用例显示“本次探测日志（收发合并）”及一个下载入口，API / 回调与媒体证据仍区分收发连接。
