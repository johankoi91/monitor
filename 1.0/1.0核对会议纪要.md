## 2. 会议目标与主要方向

本次会议评审 RTC/RTM 运维监控系统的需求边界、使用闭环、受控重启及后续黑盒探测。主要方向是先解决客户当前的监控和恢复诉求，第一版保持简单，同时把安全、资源影响和交付边界定义清楚。

本次重新整理后，需要特别保留以下内容：

| 主题 | 会议中的方向 | 仍需确认的部分 |
|---|---|---|
| 监控与恢复 | 数据提供与自动恢复分开；重启由客户发起并受规则限制 | 每个服务的允许条件、影响和禁止条件 |
| 客户接入 | 讨论了轮询和主动推送，并表达两种都做的意向 | 推送具体协议、首版范围、重试和状态同步 |
| 使用闭环 | 补齐异常发现、处理、恢复、关闭的任务流程 | 健康状态与客户告警处理状态如何同步 |
| 安全 | 不能无访问控制地开放重启；后段明确提出补鉴权并得到回应 | 鉴权方式、管理网络边界；是否需要角色体系未形成完整方案 |
| 资源与存储 | 明确 CPU/内存、存储时间和容量，优先评估复用现有组件 | 资源预算、存储选型、保留数值 |
| 自身可用性 | Agent 要有健康判断和自恢复，中心服务需考虑健康接口与高可用 | 主备和恢复机制的版本范围 |
| 黑盒 | 后续持续验证业务链路，探测位置与覆盖路径必须明确 | SDK/平台适配、网络区域、探测路径 |
| 演示形态 | 除 API 外提供最简单的 UI/Demo，降低客户理解和接入成本 | Demo 不作完整产品 UI 承诺，维护及交付范围需写清 |
| 文档组织 | 产品 PRD 与技术设计分开，先明确需求再评审实现 | 文档修订、复评与重新估算排期 |

## 3. 按会议顺序梳理讨论

### 3.1 异常发现后由谁处置（00:00–02:33）

**讨论问题：** 客户按周期查到异常后，监控系统自身是否应执行恢复动作？

介绍方案认为系统主要是数据提供方，客户监控平台查询后在自己的面板上告警。讨论要求明确“不主动恢复”的边界，避免使用者以为发现异常就一定会触发服务恢复。

**回应/方向：**

- 自动恢复和受控重启是两条不同逻辑。
- 受控重启由客户通过接口或人工发起，不是系统自行决定。
- 首期尽量先提供状态与异常信息，是否重启由客户判断；同时提供有约束的重启接口。
- 各服务是否需要立即重启、是否适合交由客户操作，需要进一步定义。

### 3.2 轮询、推送与中心数据出口（02:33–04:04）

有人询问 Agent 上报中心后，是否通过消息队列让客户消费。介绍者解释当时方案是把状态保存在中心，由客户主动查询，并不是已经确定采用消息队列。

进一步讨论客户是否只能每隔约 30 秒轮询，还是可以主动推送异常。介绍者回应提供两种方式，并表达两种都做的意向；结束前约 54:50 也再次提出异常主动推送的建议。

**纪要口径：** 轮询和推送均被讨论，不能将会议表述简化为“只做轮询”。主动推送的转写疑似指 Webhook，但术语和接口细节需回听确认；不能据此认定消息队列、Webhook 重试等技术方案已经敲定。

### 3.3 快速定位、受控重启及总体架构（04:04–05:57）

介绍的目标包括：

- 通过 API 定位宿主机、容器、镜像、异常原因和采集时间。
- 提供单节点、单容器重启接口，并回传结果。
- 在客户环境离线交付。
- 由中心服务接收每台 RTC/RTM 宿主机 Agent 的主动长连接上报。
- Agent 读取 Docker 状态，执行基础 TCP 探测和受控重启。

这部分主要是方案介绍，具体部署、协议和实现细节留待技术设计。

### 3.4 用户场景、告警处理与状态同步（05:57–10:42）

讨论指出缺少“用户应该怎么用”的完整描述：用户看到告警后如何处理、处理后如何复查，以及异常如何消失或关闭。

**讨论举例：**

- 中心返回多个异常，如何知道客户是否已处理？
- 服务自行恢复时，客户页面上的异常记录如何更新？
- 客户将告警标为已处理或关闭，是否需要回传中心？
- 客户认为磁盘或 CPU 阈值影响不大而关闭告警，中心会不会持续重复提供同一异常？

**回应/建议：** 需要明确状态变化和客户处理动作的关系，保证双方对状态的理解一致。转写约 10:00 前后存在识别缺口，具体抑制时长和重复通知策略无法可靠确认。

**未决：** 告警确认、关闭、抑制、回传或恢复通知属于讨论问题，会上未冻结接口和版本范围，不能直接认定全部进入 V1.0，也不能写成会议已经同意全部后置。

### 3.5 Agent 和中心服务的资源影响（10:42–12:06）

交付形态包含宿主机 Agent 与中心服务，讨论要求同时定义两者资源消耗和验收标准。尤其 Agent 部署在核心业务机器上，不能因自身异常、CPU/内存占用等影响原有业务。

**需要补充：** 资源预算、部署限制和异常场景下的影响验证。转写中的具体资源数字不可靠，不作为确定指标。

### 3.6 管理接口安全（12:06–12:58）

讨论指出，当前设计没有明确安全措施，能访问相关机器或接口的其他主体可能调用重启，存在业务风险，也可能在客户安全检查时被发现。

**回应/方向：** 安全必须纳入规划，不能仅因为内网部署就忽略；长期和短期方案可以分开，但首版要有实际安全边界。

该段提出的是管理 API 的访问风险，不能简单改写为“Agent 必须开放入站管理接口”；会上原架构仍是 Agent 主动连接中心。

### 3.7 数据保留、容量和超限处理（12:58–13:48）

中心存储数据时，要事先明确保存多久、容量多大、超过上限怎么办，避免新增监控系统把现场服务或磁盘拖垮。

讨论使用了保留天数和容量的例子，疑似“30 天、10 GB”，但 Tiny 识别不可靠且是举例，并未确定为产品指标。

**未决：** 状态数据、操作数据和日志的存储范围、保留期限、容量上限和清理策略。

### 3.8 平台架构及 SDK 适配（13:48–14:42）

讨论提出交付应考虑两类机器架构，并表达先实现一种、再考虑另一种的推进方式。平台名称识别不清，疑似涉及 x86/ARM，需要回听确认首期支持范围。

还提醒：基础监控适配与黑盒探测的 SDK 适配难度不同；后续业务探测依赖的 SDK 是否支持目标平台，应提前考虑，以免后续规划无法实现。

### 3.9 第一版收敛、组件复用与存储选型（14:42–20:29）

多位发言围绕“第一版是否太复杂”展开讨论：

- 先明确最终目标和版本边界，框架可以保留演进空间，但首期只实现最必要的部分。
- 当前诉求是把状态提供给客户并对接已有平台，完整管理后台可以逐步迭代。
- 每引入一个新组件都会增加部署、运维、维护和适配成本。
- 评估复用 RTC/RTM 已有监控或存储组件，避免再建设一套重复能力。
- 讨论倾向评估现有存储，而不是立即引入新的数据库；结束前也提到已有 InfluxDB 数据出口。

**未决：** 存储选型没有可靠的最终结论。Tiny 在本段对数据库和监控组件名有较多误识别，不能把讨论写成“确定使用 MySQL”“确定使用 SQLite”或“已经决定复用 InfluxDB”。

**后续安排：** 先梳理清楚需求和简化后的范围，再单独出“怎么做”的技术方案，评审组件复用及实现方式。

### 3.10 服务台账、节点基线和操作记录（20:29–22:04）

介绍方案通过配置和数据对象表达：

- 产品与服务名称、编码。
- 应有节点、宿主机、容器名。
- 检查规则和重启开关。
- 容器镜像、运行状态、错误原因和采集时间。
- 客户调用重启后的操作过程记录。

具体字段和对象结构还要在后续设计中确定。静态服务基线与动态运行状态是不同内容，应分别描述。

### 3.11 重启的业务影响与允许规则（22:04–26:11）

讨论强调，向客户提供重启相当于开放影响生产服务的操作，必须谨慎。

**关键例子：** 会中业务负载可能使 CPU 暂时到达较高水平，业务结束或系统自身调整后恢复；不能因为超过某个 CPU 阈值就要求重启。

**建议与回应：**

- 区分需要重启、不需要重启、可重启也可不重启的服务或异常情况。
- 讨论了用红黄绿或异常等级提示处置的方式，但未形成完整规则。
- 客户未必知道重启对业务的影响，不能把风险判断全部交给客户。
- 只开放有明确规则、经研发确认的低风险重启。
- 由各组件研发参与制定允许条件、参数和限制，在接口上执行这些规则。

### 3.12 原样重启与启动参数留存（26:11–28:08）

现场可能存放同一组件不同版本的启动脚本或启动参数。只记录 Container ID，不足以支撑涉及重建的恢复操作。

**讨论提出的原则：** 尽量原模原样恢复重启前的容器，保持原镜像和原参数，避免误启动另一版本。

建议部署后获取现有容器的实际启动信息并留存。讨论区分了简单 restart 与重新创建实例：若只是重启现有容器，问题相对简单；若删除后重建，则必须还原原配置。

**未决：** 是否扩展到重建实例、保存哪些参数及存在哪里没有冻结。不能把该段直接当作 V1.0 已承诺重建容器。

### 3.13 业界参考和健康分层（28:08–30:00）

介绍了参考知名服务端组件监控设计的思路：

- 状态应分层，容器可用不等于业务可用。
- 主动长连接用于采集。
- V1.0 先使用三个层面的通用证据。
- 后续版本增加黑盒业务探测。

本段对组件健康设计原则主要作概括介绍，没有逐项评审各开源组件的指标适配。

### 3.14 首期服务目录、配置方式与 Agent 采集（30:00–34:09）

首期选取重点 RTC/RTM 服务；监控支撑组件暂不直接纳入业务基线。具体名单和版本差异还需与各模块研发核对。

配置从客户部署脚本、目录和机器清单生成，首版使用固定格式的文件。脚本生成或可视化编辑被作为后续改进方向提出。

每台相关宿主机部署 Agent，收集本机服务状态，主动连接中心，介绍的默认采集周期为 15 秒；Agent 异常或失联需让中心感知。容器身份、镜像和运行状态等作为采集内容。

**识别限制：** 约 30:00–30:30 有明显重复识别，不能从 Tiny 确认完整 RTC 名单或某个待补服务的名称。

### 3.15 UDP、本机端口检查和业务探测的区别（34:09–37:37）

讨论是否需要补 UDP 探测，以及采用 iperf 还是由研发提供更合适的方法。

**主要意见：**

- 本机检查只能反映本机端口或服务监听情况，不能证明完整路径、节点间网络和业务通路正常。
- 端口检查与后续黑盒有部分目标重叠，但是否保留、如何组合仍需评估。
- 黑盒应是持续运行的真实端到端验证，不能只等同于一次部署前的网络检测。
- 服务端发起探测与客户 PC 到服务端的实际路径不同，结果的覆盖范围必须说明。

**未决：** UDP 方法、iperf 的具体使用方式、黑盒是否提前进入首版均未最终确定。该段有重复和缺失，不能根据 Tiny 重建不存在的协议细节。

### 3.16 黑盒路径覆盖与探测发起点（37:37–40:00）

讨论指出，只看本机容器不能发现节点间网络异常。业务探测需要明确连接哪个入口、分配到哪个节点，以及覆盖哪些节点组合。

同时质疑全互联探测是否必要：五台机器若互相探测其他四台，会扩大复杂度和影响系统架构。

**回应/方向：** V1.0 Agent 收集本机信息；V1.1 黑盒应由独立的探测服务或集中发起点执行，不要求每台 Agent 都跑一套业务探测。具体发起位置、目标控制和路径覆盖仍需设计。

端口清单应以实际部署和研发提供的标准为准。

### 3.17 状态、防抖和监控系统自身可用性（40:00–44:31）

介绍健康、异常、未知三种节点状态，并讨论状态更新不能漏掉恢复变化。TCP 检查采用多次确认，Agent 无上报采用超时判断；V1.1 再增加黑盒相关结果。

讨论随后转向监控自身：

- Agent 失联后如何恢复，客户要做什么，需要定义。
- Agent 本身要有健康判断；中心服务应提供客户能调用的健康接口。
- 提出主备、高可用和异常拉起机制，并讨论复杂度。
- Agent 至少应考虑自身恢复；宿主机本身异常无法仅靠 Agent 自恢复解决。
- 中心服务高可用可以参考已有组件，但方案没有最终冻结。

**未决：** 是否部署双 Agent、中心主备、数据如何同步、进入哪个版本，均待技术设计，不能写成已选定架构。

### 3.18 状态 API、重启规则、错误反馈与审计（44:31–48:15）

介绍对外能力：

- 版本化状态和操作接口，支持按服务编码、状态筛选。
- 返回各状态节点数、节点明细、原因和采集时间。
- 查询读取缓存，不同步触发探测。
- 节点异常通过响应内容表达，介绍方案仍返回 HTTP 200。
- 支持查询单次操作结果。

重启需要避免重复操作、限制同节点并发，并记录过程和结果。执行前依据原容器信息和允许规则判定，再下发操作。接口请求、响应和错误说明需随讨论调整，错误反馈应包含真实原因。

操作审计要能追溯何时、对哪个对象执行了什么，以及结果如何。

**识别限制：** 约 46:25–46:37 疑似涉及多个异常节点操作，文字不清，无法确认是否提出批量重启，更不能认定批量操作已进入首版。

### 3.19 鉴权补充、验收与排期调整（48:15–50:43）

介绍者表示会补充接口查询频率及资源占用等非功能要求。讨论再次明确提出鉴权应做，介绍者回应此前设计未加，此次补进去。

**会议方向：** 安全不能只放在长期规划里，需要补进当前设计和验收。具体鉴权及安全实现仍待确定；这不等于会议已确定多用户角色、审批或完整权限平台。

验收应与前面功能和操作结果对应。由于会议新增及调整了要求，介绍者表示排期可能需要调整，未确认新的交付日期。

### 3.20 未决映射、版本适配与 V1.1 规划（50:43–54:38）

继续讨论服务对象定义、现场节点配置、版本变化和核心服务重启影响。首版先用标准样例文件；服务、端口和镜像差异要按实际目标版本适配，单点核心服务重启风险通过规则和白名单控制。

V1.1 介绍的方向：

- RTC：加入频道、发布/接收测试流、离开，记录阶段结果。
- RTM：登录、消息收发等真实业务步骤，记录并上报结果。
- 探测失败后是否触发重启规则，仅作为后续评估问题。

介绍者还表示，需要调整“暂不包含”中关于角色、权限的表述，加入前面讨论的鉴权限制。不能继续把本次会议总结为“一致同意完全不做鉴权”。
