## Key 申请与使用

登录页：申请名称 → 用途（登录 / 重启 RESTful）→ 原因 → 提交 → 申请编号。申请不会自动登录、生成有效凭证或开放白名单。管理端现场核实后，在“接入密钥”选择申请、填写签发依据；重启用途必须明确勾选基线节点，再签发。Secret 只在签发响应显示一次，由管理端安全交付，丢失后重新签发并停用旧 Key。

| 凭证 | 登录/业务查询及配置 | 密钥签发/停用 | 重启/未知结果核实 |
|---|---|---|---|
| 初始化管理凭证 | 允许 | 允许 | 拒绝，须另用 RESTART Key |
| CONSOLE 登录 Key | 允许 | 拒绝 | 拒绝 |
| RESTART 安全 Key | 控制台及配置拒绝；可查授权节点单次操作/审计 | 拒绝 | 只在授权节点范围内，继续核验双端规则 |
| 待处理申请编号 | 拒绝 | 拒绝 | 拒绝 |
| 已停用 Key | 拒绝 | 拒绝 | 拒绝 |

以上区分系统凭证用途，不增加个人账号、用户角色或业务审批平台。申请名称和 operator 都不等同于认证个人身份；操作另存真实 Key ID、来源 IP、节点及阶段证据。

注册记录在中心 `access-keys.jsonl`，0600、fsync、独占锁、16 MiB 上限，仅存 Secret SHA-256 哈希；申请最多 1000 个。两次部署重启后已签发/停用及节点范围保持。浏览器凭证仅在当前内存，退出/刷新清空；重启/核实框另填安全 Key。Agent/通知凭证保持独立。

## 真实恢复证据

停止后中心识别 `CONTAINER_EXITED / UNHEALTHY`。通过 RESTART Key 受理操作 `33857905465d56894bc23c30438b156e`，request_key=`demo-recovery-20261006`。

| 证据 | 实测值 |
|---|---|
| 受理时间 | 01:05:36.245 |
| Docker 启动前时间 | 00:57:33.661 |
| Docker 启动后时间 | 01:05:38.360 |
| 完成时间 / 耗时 | 01:06:01.621 / 25,376 ms |
| 容器 ID | `c6bdefb92263630ec1df3271336e1001b8839aeb25f5b88ebbd009c04240803c`，前后一致 |
| 镜像 | `avops-canary:1.0.0`，前后一致 |
| 配置快照指纹 | `51ca032d885897b105389869a5489c900841a215e95df5fa2f08ee70e9fdbe61`，前后一致 |
| 结果 | SUCCESS / HEALTHY / result_known=true / node_locked=false |

中心审计完整记录 ACCEPTED → PREPARED → EXECUTING → EXECUTED → VERIFY_SUCCESS；Agent 日志只有该操作的 PREPARED、EXECUTING、EXECUTED 各一条。Docker 返回后还等待新采集与 TCP 18098 连续两次成功，未直接把 Docker 返回当作健康恢复。该结果验证容器与浅层 Readiness，不证明 RTC 真实业务流程成功。

相同 request_key、相同参数重放返回 HTTP 202 和同一 operation_id；改变原因后重用同键返回 409 IDEMPOTENCY_CONFLICT。最后一次中心/UI 升级重启后再次重放仍返回原 SUCCESS 操作，Agent 未重复执行，Docker StartedAt 未再次改变。

|---|---|---|
| 演练节点 UNHEALTHY | `def628070e6911fd345786f30454c61d` | 01:01:05.626 |
