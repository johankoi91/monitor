# 运维监控通用凭证模型设计

## 目标

将 Agent、通知接收端和重启 RESTful 调用统一到同一种机器凭证协议和生命周期管理方式，同时保留不同用途之间的隔离。

## 统一规则

凭证统一包含：凭证 ID、类型、所属账号、权限作用域、节点范围、启停状态、有效期、轮换关系、创建/停用审计。机器调用统一使用：

```http
Authorization: Basic Base64(credential_id:secret)
```

中心在请求进入业务逻辑前统一校验：凭证格式 → 是否启用/过期 → 用途是否匹配 → 节点范围 → 账号角色 → 白名单/现场状态。

## 三类凭证

| 类型 | 方向 | 存储 | 作用 |
|---|---|---|---|
| AGENT | Agent → 中心 | 部署配置及受保护环境 | Agent 上报、接收自身任务 |
| NOTIFICATION_RECEIVER | 中心 → 接收端 | PostgreSQL AES-256-GCM | 只向配置的通知 URL 投递 |
| RESTART | 机器/RESTful → 中心 | 中心只存 Secret 哈希 | 只操作授权节点的重启 |

通知接收端凭证不能用于 Agent 或重启；RESTART 凭证不能登录页面、修改台账或签发其他凭证。人工重启仍使用账号 Bearer 会话叠加 RESTART Key，以同时证明人员权限和高风险操作凭证。

## 当前实现映射

- Agent Basic 凭证继续来自 Agent 部署配置。
- 通知页面保存 URL、TLS ServerName 和独立接收端 ID/Secret；Secret 加密保存，GET 不返回 Secret。
- 重启安全 Key 在 PostgreSQL/接入密钥注册表中保存哈希，必须绑定节点范围。
- 历史列表不提供旧 Secret 的直接复制，因为旧 Secret 不可恢复；“轮换并复制新密钥”会签发新 Secret、自动复制并停用旧 Key。
- 历史 CONSOLE Key 已停用，不再新签发；后续凭证类型只允许上述三类。

统一模型不会把不同系统的 Secret 合并为一把“万能 Key”，而是统一校验方式、审计字段、轮换和停用流程。
