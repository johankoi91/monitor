## 2. V1.0 改进项

### IMP-01 补齐异常发现、客户处置、恢复复查和关闭边界

**问题：** 现有方案说明了状态和重启 API，但没有完整回答客户发现异常后如何处理，以及客户“已处理/已关闭”是否改变服务健康状态。

**改进与验收：** 补充“查询/接收状态 → 客户侧告警 → 定位节点 → 人工判断 → 允许时重启 → 查询结果 → 重新查询健康状态”的闭环。客户确认、关闭或抑制告警不改变中心采集事实；CPU 短时升高不直接触发重启。演示容器故障、受控重启、自行恢复和 Agent 失联四类流程。

融合评审：在 PRD 增加独立的“使用者、任务与场景”章节，用“触发 → 主路径 → 接口/数据 → 验收”表达日常使用，补齐缺失节点可见、现场台账维护和业务可用性误判防护等场景。明确谁负责轮询接入、谁维护 YAML、谁发起重启和核对结果、谁验收网络安全；这是交付分工，不是产品角色权限。轮询 30 秒时故障发现不超过 60 秒等指标应与 PRD 一致，并说明采集及客户查询周期的前提。

评审来源：评分表“用户与场景”、最弱一节、四人面板“最终用户”、拟改写 §2.x、Must-fix 第 1 项。产出：任务场景表、接入流程、交付分工说明。

来源：纪要 3.4、A-010；视频约 `05:57–10:42`。

### IMP-02 决定轮询与主动推送的版本范围

**问题：** 会议前段说明客户主动轮询，随后表达轮询和主动推送两种方式都会做，当前契约主要只有轮询。

**改进与验收：** 已确认 V1.0 同时轮询与推送，中心支持配置一个 HTTP/HTTPS 通知地址。定义 POST JSON、状态变化和恢复、事件 ID 去重、有限重试、超时和失败处理；通知不阻塞查询，不引入消息队列，不把推送继续列作是否纳入的待决事项。

来源：纪要 3.2、A-001；视频约 `02:33–04:04`、`54:50` 左右。

### IMP-03 可视化建立现场服务、节点、容器和端口基线

**问题：** 服务目录、RTM AP、容器名、端口和版本存在现场差异，Tiny 无法确认完整名单。

**改进与验收：** Agent 发现本机所有可见 Docker 容器，含运行和停止实例；中心汇总所有已接入机器。界面默认运行态，支持按主机/Agent、名称、镜像和状态筛选及多选，指定集群/逻辑服务后预览差异。保存自动生成 YAML，记录服务编码、Agent、稳定节点 ID、精确容器名、检查规则和重启开关。端口确认协议和监听地址，纯 UDP 不配置 TCP 检查；删除应有容器后仍显示 MISSING。RTM AP 后置，不阻塞 RTC。

融合评审：记录端口与现场启动参数（如实际使用的 `agora_media_server_port`）或 `mgmt.sh` 的对应关系，明确 YAML 生成、复核、分发和生效方式。OPEN-001 已按用户选择从 RTC 首期后置，待 RTM 接入时再完成映射；不以未知对象安排验收。

保存时校验 YAML 格式、字段、重复节点 ID、候选在线/新鲜状态与身份/配置快照；现场复核镜像、端口和服务映射。提交携带基线版本，避免并发覆盖；成功后可靠落盘并立即生效，无需重新编译或重启中心，支持下载和中心重启恢复。校验/保存失败保留旧版本。

既有基线成员包括缺失/失联节点，不能因筛选、分页、刷新或发现结果不包含它们而移出；提交仅表达明确新增/移出。未变更的离线成员不阻止其他正常候选纳管；新增容器不自动入基线，新增节点默认禁重启。重启执行中的节点不可移出或改绑定。启动配置保存在独立脱敏快照，不塞入 YAML。

评审来源：四人面板“研发/交付”、拟改写场景 5、Must-fix 第 3 项、Nice-to-fix 第 3 项。产出：版本映射表、分发说明、现场核对记录和 OPEN-001 关闭记录。

来源：纪要 3.10、3.14、3.20、A-002；视频约 `20:29–22:04`、`30:00–34:09`、`50:43–52:32`。

### IMP-04 统一健康分层、失联、防抖和恢复口径

**问题：** Agent 长连接、有效上报、状态过期、容器状态和 Readiness 容易混淆。

**改进与验收：** 统一 `AGENT / CONTAINER / READINESS`，V1.1 增加 `BLACKBOX`；按有效上报判断 Agent 新鲜度；容器异常、TCP 防抖和恢复规则统一写入 PRD、原型、OpenAPI；监控自身健康与业务服务健康分开。容器 running 但 Readiness 不通过时不得返回业务可用。

融合评审：V1.0 对外明确只描述容器和浅层 Readiness，不承诺完整 RTC/RTM 业务可用。应有节点数不因容器删除而减少；层级、原因码、采集时间和 stale 均作为证据返回。故障判定、防抖和 30/60 秒时效按故障类型分别验收，不把 TCP 连续失败确认时间误套成容器退出的发现时限。

评审来源：拟改写场景 1–3、6，四人面板“负责人/商务”，附录“做得好的地方”。

来源：纪要 3.13、3.17、A-005、A-012；视频约 `28:08–30:00`、`40:00–44:31`。

### IMP-05 制定按服务区分的重启白名单与风险规则

**问题：** `restart_enabled` 只是开关，没有明确哪些服务必须、禁止或允许重启。

**改进与验收：** 各模块研发制定服务级允许条件、禁止条件、业务影响和低风险白名单；不把所有异常或 CPU 阈值视为重启条件，不扩展为批量重启或任意命令。核心高影响服务未确认前默认关闭，规则违反时返回可解释错误。

融合评审：唯一 AP 等核心单点节点默认 `restart_enabled=false`，研发评审后逐个开放；目标白名单与请求鉴权/来源控制是独立检查，不能用操作人字符串或节点白名单代替访问控制。

评审来源：拟改写安全前提第 3 项、四人面板“负责人/商务”、Hard block 第 1 项。

来源：纪要 3.1、3.11、A-003；视频约 `00:00–02:33`、`22:04–26:11`。

### IMP-06 上报启动配置并确保原容器重启一致性

**问题：** 同一目录可能有多个版本和启动参数，只依赖 Container ID 或通用启动脚本可能重启错版本。

**改进与验收：** Agent 从 Docker 实际 inspect 中提取镜像引用/ID、Entrypoint/Cmd、实际 Path/Args、环境变量、工作目录、运行用户、挂载、端口、网络模式和重启策略；首次发现、身份或配置变化时上报详情，页面展示配置快照时间、指纹及脱敏/不完整标记。旧 Docker 缺字段兼容，取不全不得伪装完整。

环境变量值默认隐藏，命令凭证和 URL 内嵌凭证等在 Agent 上报前脱敏；不上传原始 inspect，不把敏感原值写入普通日志、通知或 YAML。配置摘要是事实证据，不自动改基线、开放重启或生成可执行重建命令。

V1.0 执行核验后的原容器 `docker restart`；涉及重建时再单独设计。重启前后配置一致，容器被替换或不匹配时拒绝。采集验收与重启演练分别验证，不以脱敏快照宣称可以完整还原部署脚本。

来源：纪要 3.12、A-004；视频约 `26:11–28:08`。

### IMP-07 完善重启幂等、并发、中断和错误反馈

**问题：** 执行中断、结果未知、中心重启和相同幂等键参数不一致时的行为尚未明确。

**改进与验收：** 保留幂等键、本地持久化、同节点并发限制、操作状态和审计；定义受理、下发、执行、复查各阶段中断处理，不盲目重新下发；错误响应包含真实原因，操作可追溯。

融合评审：审计中区分“已鉴别的调用来源”与“调用方填写的 operator”。未建立个人账号时不能声称 operator 已验证为真实个人；明确审计记录的导出/查看方式及交付责任，保持单次结果查询和本地审计的首版边界。

评审来源：四人面板“负责人/商务”，Hard block 第 1 项。审计来源细化为本次融合建议。

来源：纪要 3.18、A-013；视频约 `44:31–48:15`。中断细化为整理建议。

### IMP-08 将鉴权和管理通道安全纳入 V1.0

**问题：** 会议前段指出能访问接口就可能重启，后段明确提出补鉴权；现有 PRD 仍写成完全不提供鉴权。

**改进与验收：** HTTP Basic Auth 已确认，使用本系统自有接入 ID/密钥，参考声网认证格式；不增加角色/审批体系。来源、Agent 身份、HTTPS/WSS 和 Docker Socket 边界在实施中落实；缺失或错误认证不能重启。实际凭证不写入仓库或前端。

融合评审：把管理网隔离、源 IP 白名单和 Docker Socket 风险审批写成可检查的交付条件；网络 ACL 不能替代会议要求补入的鉴权。Agent 只出站连接中心，交付说明列出目标 IP、端口和协议，不增加入站管理端口。验证未批准来源、无凭证/无效凭证的请求均不能执行重启。

对明文 HTTP/WS 风险，记录目标客户是否允许，以及传输保护与证书的落地方式：评审直连 HTTPS/WSS、复用客户反向代理等方案及证书交付责任，不默认恢复完整 mTLS 或账号体系。客户安全条件未满足时，不能把该环境作为正式重启交付验收环境。

评审来源：Hard block 第 1 项、评分表“私有化完备性”、四人面板“交付/最终用户”、拟改写 §2.x.3、Must-fix 第 1 项。产出：安全设计、网络/证书清单、准入及拒绝用例、客户安全验收记录。

来源：纪要 3.6、3.19、A-006；视频约 `12:06–12:58`、`48:15–50:43`。

### IMP-09 定义 Agent 与中心服务资源预算与隔离

**问题：** Agent 与业务容器同机，异常采集、重连、探测和日志可能抢占业务资源。

**改进与验收：** 测量正常、高峰、Docker 无响应、网络断开和中心不可达场景，确认 CPU、内存、磁盘、网络、并发、超时、退避和日志上限；会议中的数字仅作例子，确认前不写成指标。

融合评审：分别列出中心和 Agent 的最低部署规格、目标规模及允许的资源开销；不能仅有资源上限而没有安装下限。资源预算、API 延迟和节点规模一并确认后再进行验收。

评审来源：评分表“产品形态”、Nice-to-fix 第 3 项。产出：最低规格与资源预算表。

来源：纪要 3.5、A-005；视频约 `10:42–12:06`。

### IMP-10 决定状态、操作、审计和日志的存储复用方案

**问题：** 会议讨论复用现有组件、数据库和 InfluxDB，但没有最终选型；保留周期和容量也未冻结。

**改进与验收：** 分别定义最新状态、操作索引、审计和历史数据需求，评估现有组件与本地方案的离线部署、备份、容量和清理成本。不得把 Tiny 中不可靠的数据库名或“30 天/容量”例子写成结论；存储写满时不能继续受理无法记录的重启。

来源：纪要 3.7、3.9、A-007；视频约 `12:58–13:48`、`14:42–20:29`。

### IMP-11 明确监控系统自身健康、自恢复和高可用边界

**问题：** Agent/中心服务自身失效时，客户如何发现和恢复尚未完整定义；双 Agent、主备和同步未冻结。

**改进与验收：** 实现 Agent/中心健康、失联超时、中心重启状态空窗和操作索引恢复；Agent 进程拉起、重连保留，宿主机故障不承诺自修复。单中心已确认，主备和双 Agent 后置；停止 Agent 后节点 UNKNOWN，旧数据不得冒充新状态。

融合评审：写明冷启动阶段的状态接口行为。配置加载完成但尚未收到新快照时，应保留应有节点清单，将相关节点显示为 UNKNOWN 并表达新鲜度，不能返回“0/0 正常”；中心自身已就绪也不代表业务节点已健康。明确新快照重建窗口、部分 Agent 上报时的聚合规则和超时后处理，窗口数值随采集周期及现场测试确认。

验收补充：中心重启后在第一份新快照前、部分 Agent 恢复时、全部 Agent 恢复时分别查询；节点基线和健康判定连续一致，旧时间戳不会被改为新的采集时间。

评审来源：四人面板“研发”、Nice-to-fix 第 2 项。产出：冷启动 NFR、接口示例和故障恢复报告。

来源：纪要 3.17、A-012；视频约 `40:00–44:31`。

### IMP-12 拆分 PRD 与技术设计并重新估算排期

**问题：** 需求、架构、组件、存储、安全和实现细节混在一起；会议认为首版过重，新增要求会影响原排期。

**改进与验收：** PRD 保留产品要求，技术设计承接实施细节；已确认 RTC 范围可推进实现，存储/平台/资源在实施核对。按用户要求不把负责人和日期列为当前启动门槛，也不沿用未经验证的历史排期。

融合评审：单独列出实际可复用的控制端/Agent 能力、缺口和新建工作量，不能把“可能复用”当成排期前提已满足；区分工作日与人日，明确投入人数及现场配合。使用场景、安全方案、评审契约和 RTM AP 纳管结论完成确认后，再进入研发排期评审。

评审来源：四人面板“交付/SA”、Verdict 与 Must-fix。产出：范围冻结记录、复用盘点、资源投入与排期估算。

来源：纪要 3.9、3.21、3.22、A-009、A-015；视频约 `14:42–20:29`、`54:38–01:01:29`。

### IMP-14 提供状态/启动详情页面及正式基线保存界面

**问题：** 会议认为只讲 API 对客户理解和演示不够直观，提出提供简单 UI/Demo，但不等于完整管理后台。

**改进与验收：** 在 111.230.108.76 提供 RTC 状态、原因、时间、受控重启结果，以及容器发现、脱敏启动详情、筛选归类、差异预览、保存生效和 YAML 下载。页面使用同一 Basic Auth/API，交付源文件和启动说明，不增加角色体系、历史曲线或告警中心。

状态/重启页面保留 Demo 交付边界；可视化基线保存是正式功能，必须由中心校验并可靠持久化，不能用前端勾选样例替代。验证多机发现、过滤不误删、版本冲突、候选过期、保存失败和中心恢复；当前 Mock 无这些新增能力，按 PRD AC-20 至 AC-26 验收真实实现。

来源：纪要 3.21、A-014；视频约 `58:22–59:38`。

### IMP-15 确认 CPU 架构、SDK 平台和黑盒适配范围

**问题：** 会议提到两类机器架构和后续 SDK 适配，但平台名称及首期顺序无法从 Tiny 确认。

**改进与验收：** 冻结首期 x86/ARM 支持矩阵、镜像/二进制交付方式和客户环境；分别评估 V1.0 Agent/中心与 V1.1 RTC/RTM SDK 的平台可用性，不为未确认平台承诺交付。

融合评审：产品经理明确提出 x86/ARM 交付规格；会议中平台名仍属不清楚内容，两类来源分别记录。支持矩阵还应列出最低环境版本、离线依赖和对应架构包，按实际首期支持范围验收，不默认承诺双架构同时交付。

评审来源：评分表“产品形态”、Nice-to-fix 第 3 项。

来源：纪要 3.8、A-011；视频约 `13:48–14:42`。

### IMP-17 补齐评审包及契约一致性验证

**问题：** 独立评审时只有 PRD 正文，引用的 OpenAPI 和 YAML 示例不在评审材料内；当前工作区已有文件，但不能据此认定每次评审和离线交付都会附齐。

**改进：** 将 PRD、原型、OpenAPI、YAML 示例、运行说明和必要的现场映射依据作为同一评审包，保留相对路径或明确版本。验证字段、枚举、路径、状态规则和例子的一致性；Mock 与正式能力分别说明，不用 Mock 编译通过替代真实 Agent 验收。

**验收：** 将评审包复制到独立目录后，所有链接可打开，契约可解析，状态和单次重启示例可按说明执行；节点数量、原因和层级与 PRD 一致。附件缺失的问题关闭，契约正确性另按场景验证。

产出：评审包清单、版本记录、契约一致性检查结果。来源：评审 What I read、Hard block 第 3 项、评分表“功能可验收”、Must-fix 第 2 项。

### IMP-18 建立待决事项负责人、期限和关闭机制

**问题：** OPEN 项、会议 A 项和改进项只有建议负责方，缺具体 Owner、期限、证据及延期对排期的影响。

**改进：** 当前先记录用户确认结果、实施参数和 OPEN/A/IMP 对应关系。按用户要求暂不指定个人 Owner、日期或签字，不把它们作为开发门槛；后续正式交付安排再补，不虚构人员或期限。

**验收：** 本次 RTC 范围、Basic Auth、推送、Demo 和单中心的确认可追溯；RTM AP 后置，未核对实施参数不虚构已完成。人员和日期缺失不阻塞开发。

产出：决策台账、关闭证据和排期影响记录。来源：评分表“风险与待确认”、Nice-to-fix 第 2 项、Must-fix 第 3 项；关联会议 A-001 至 A-015。

### IMP-19 集中列明版本范围、非目标和对外承诺

**问题：** 非目标散落在架构和 V1.1 规划中；会议对鉴权、推送和 Demo 的补充与旧版边界存在差异。

**改进：** 在 PRD 集中用一张表列出 V1.0、V1.1 和待决能力。完整产品 UI 与最小 Demo 分开，用户角色体系与系统鉴权分开，业务自动恢复与 Agent 自恢复分开。明确告警中心、业务黑盒、历史时序、日志采集、自动编排、HTTPS/WSS 和 mTLS 的实际范围及决策状态，不把旧版“非目标”未经评审直接沿用。

**验收：** 范围表与功能、接口、Demo、验收和交付说明一致；V1.0 不宣称业务链路健康，V1.1 黑盒结果注明探测路径和覆盖范围。“未纳入”不免除必要的部署和安全条件。

产出：版本范围/非目标表、对外接入与交付口径。来源：评分表“范围控制”、Nice-to-fix 第 1 项、四人面板“负责人/商务”；会议 3.19–3.21。

### IMP-20 明确交付、验收及签字责任

**问题：** 产品价值与 30/60 秒目标较明确，但谁确认现场台账、谁批准 Docker Socket 使用、谁验收接口和最终签字没有落地。

**改进：** 当前保留试点功能、网络、安全及演练记录，不指定个人责任、日期和签字方，不引入角色权限。正式交付安排后续再补，不阻塞 RTC 首期开发。

**验收：** 客户轮询周期、发现时延和安全条件由对应验收方确认；台账、接口、拒绝重启、幂等、恢复等演练有结果及确认记录。只承诺当前检查层级内可验证的行为，不以一份自填 operator 记录代替身份或责任确认。

产出：交付责任表、验收清单、确认/签字记录。来源：评分表“问题清晰度”、四人面板“交付/负责人/最终用户”、拟改写目标用户表；会议 A-005、A-006、A-013。

## 3. V1.1 规划改进项

### IMP-13 按真实网络路径规划独立黑盒探针

**问题：** 本机探测无法覆盖客户端到服务、节点之间和不同网络区域的异常；每台机器全互联探测会放大复杂度。

**改进与验收：** 独立部署探针，明确探测位置、网络区域、源位置、目标服务、路径和覆盖盲区。RTC 覆盖加入、发布、接收媒体帧、离开；RTM 覆盖登录、消息收发、登出；记录阶段结果、耗时和原因；不默认每台 Agent 运行完整业务探针；失败先更新状态，不自动重启。

来源：纪要 3.15、3.16、3.20、A-008；视频约 `34:09–40:00`、`50:43–54:38`。

### IMP-16 服务特有指标与可复用监控底座边界

**问题：** 会议希望形成可扩展底座，但服务特有指标和其他模块扩展不能反向膨胀 V1.0。

**改进与验收：** 保留通用服务、节点、检查层级、原因码和状态 API；后续按产品能力增加 RTM 同步、RTC 会话/媒体等证据。评估组件复用和扩展契约，不在本项直接写死组件选型。

来源：纪要 3.9、3.13、3.21；视频约 `14:42–20:29`、`28:08–30:00`、`54:38–59:38`。

## 7. 融合后复评关闭条件

1. 使用场景、任务分工、版本范围和非目标集中写入 PRD，客户能理解日常操作路径。
2. 鉴权、网络及传输方案和 Docker Socket 边界有实际验收证据，核心单点重启默认收紧。
3. 评审包附件齐备，契约/Mock/正式能力差异明确；RTC 现场基线可核对，RTM AP 已记录后置范围。
4. 冷启动、状态新鲜度、资源规格和现场台账核对有定义及验证方式。
5. 保留用户确认及实施记录；实际 Owner、日期和签字按用户要求后续安排，不作为本次开发启动条件。
